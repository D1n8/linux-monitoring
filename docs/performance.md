# Измерение расходов · 18 ноября 2026

Проверено на Linux x86_64, ядро 6.17.0-35-generic, AMD Ryzen 5 5500U, 12 логических CPU, 7,1 GiB RAM. Docker Engine 29.8.2, PostgreSQL 17, один Go-сборщик. Это рабочая машина с фоновыми задачами, а не изолированный VPS.

## Методика

Три сценария по 60 секунд после подготовки соединений: выключенный сбор, один и пять дополнительных зрителей. Одно фоновое SSE-подключение оставалось открытым, поэтому фактическое число зрителей — 1, 2 и 6. Скрипт записал диапазон числа подключений; он был постоянным внутри каждого сценария. Все созданные тестовые потоки оставались подключены до окончания замера.

Каждый тестовый зритель читает SSE, запрашивает host/health раз в 10 секунд и историю раз в 30 секунд. Первый запрос истории выполнен до измерительного окна. Диагностический запрос snapshot выполняется раз в 5 секунд. Это измерение серверной части; браузерная отрисовка, Docker Engine и затраты первой сборки в цифры контейнеров не входят.

- CPU = разница накопленного container cpu_usage.total_usage / фактическое время. **100% соответствует одному логическому ядру**, без деления на 12 CPU хоста.
- Память = usage − inactive_file (рабочий набор без неактивного файлового кеша), снимки раз в 5 секунд. Максимум ниже — максимум среди снимков, не непрерывно измеренный пик.
- I/O = разница счётчиков блочного устройства контейнера. Она зависит от файлового кеша и момента checkpoint PostgreSQL; отсутствие block I/O не означает отсутствие SQL-записей.
- Пропуски/потери и число циклов берутся из health. Выключение — состояние планировщика с завершённой очередью, а не пауза браузера.

## Что сократили по результатам проверки

Первые настройки запускали healthcheck Go раз в 10 секунд, PostgreSQL — раз в 5 секунд. Это создавало постоянные расходы даже при выключенном сборе. В итоговой версии обе проверки идут раз в 30 секунд, а при старте — раз в 2 секунды. До изменения в коротком прогоне при 6 зрителях зафиксировано 1,66% одного ядра суммарно, в итоговом — 0,96%. Это последовательные наблюдения на общей машине; они не дают универсального процента улучшения для любого VPS.

Небольшие расходы обеспечиваются прямым чтением счётчиков, одним сборщиком, кешированием метаданных, пакетами до пяти снимков, ограниченными очередями и статическим Nuxt-интерфейсом. Удалены пороговые правила и обработка событий. PostgreSQL сохраняет собственные постоянные расходы даже при остановке сбора. Для полного выключения обоих контейнеров используется `./stop.sh`.

## Как повторить

```bash
python3 scripts/benchmark.py --seconds 60 --output /tmp/goinmetrics-performance.json
go test ./internal/collector -run '^$' -bench BenchmarkCollect -benchmem -benchtime=3s -count=3
```

Скрипт требует работающего сервиса, Python 3 и доступа к Docker Engine. Он временно выключает сбор (появится разрыв истории), создаёт тестовых зрителей и в конце возвращает исходное состояние. Во время теста не перезапускайте контейнеры и не переключайте мониторинг вручную.

Исходные данные: [итоговый JSON](benchmarks/2026-11-18.json), [прогон до изменения healthcheck](benchmarks/2026-11-18-before-healthchecks.json), [микробенчмарк](benchmarks/collector-2026-11-18.txt).

Цифры подтверждают небольшой расход в этом сценарии. Суточный рост БД, разные типы VPS, множество ресурсов и влияние на задержки конкретного приложения требуют отдельного испытания. Утверждение о наименьшем расходе среди всех аналогов не проверялось.
