# Проверка MVP

## Воспроизводимые проверки

```bash
make test
make build
./start.sh
```

`make test` проверяет Go с race detector, `go vet` и типы Vue/TypeScript. При наличии сгенерированного интерфейса Go-тест дополнительно проверяет, что ресурсы `/_nuxt/` действительно встроены и CSS отдаётся с верным MIME. Это защищает от особенности `go:embed`, по умолчанию пропускающего каталоги с `_` в начале имени; используется `all:public`.

Интеграционный тест запускается только при явной переменной `TEST_DATABASE_URL`. **Укажите отдельную пустую тестовую БД**: тест очищает samples/events и меняет правила. Для примера временная БД, закрытая на loopback:

```bash
docker run -d --rm --name goinmetrics-test-db \
  -e POSTGRES_USER=goinmetrics -e POSTGRES_DB=goinmetrics_test \
  -e POSTGRES_PASSWORD=integration-only \
  -p 127.0.0.1:15439:5432 postgres:17-alpine
# После готовности PostgreSQL:
TEST_DATABASE_URL='postgres://goinmetrics:integration-only@127.0.0.1:15439/goinmetrics_test?sslmode=disable' \
  go test -race ./internal/store -v
docker stop goinmetrics-test-db
```

CI в `.github/workflows/ci.yml` создаёт PostgreSQL service, собирает Nuxt, проверяет типы, Go-тесты и сборку. Ничего не публикует.

## Что проверяют тесты

- CPU не учитывает guest повторно; неполные данные отклоняются.
- MemAvailable корректно исключает доступный кеш.
- Сеть учитывает фактический интервал, новые/сброшенные счётчики дают `null`.
- Отказ CPU не отменяет память; некорректные числовые счётчики не превращаются в нулевые.
- API разрешает локальный адрес и SSH-туннель, отклоняет сторонний Host/Origin и cross-site запрос.
- Некорректные периоды отклоняются до обращения к БД; правила валидируются.
- Реальная PostgreSQL: запись/чтение истории, достижение длительности порога, resolved/interrupted, разрыв и восстановление после перезапуска, очистка старых измерений.

## Ручная проверка сценариев

1. Запустить `./start.sh`: оба контейнера healthy, `/api/health` отвечает 200. Создание правил не требуется для первых графиков.
2. На первом чтении CPU/сеть показывают подготовку, затем — реальные значения. Сопоставить CPU с `top`, память с `free`, диски с `df`; определения метрик могут отличаться.
3. Открыть вторую вкладку: метки времени совпадают, новый сборщик не создаётся.
4. Проверить 15 минут / 1 час / 6 часов / сутки, переключение ресурса, CSV и мобильную ширину 390 px.
5. Включить CPU-правило с порогом 0 и длительностью 1 секунду. После ненулевой нагрузки и обновления метаданных появится событие. Открыть его график; выключить правило и вернуть подходящие значения.
6. Перезапустить приложение: история и правила остались, активное событие стало interrupted.
7. На тестовом окружении приостановить БД: `docker compose pause postgres`. Через несколько секунд health становится 503, интерфейс сообщает об ошибке записи; `/api/snapshot` продолжает обновляться. Затем `docker compose unpause postgres`: запись восстанавливается, несохранённые точки не выдумываются.
8. Отключить соединение браузера: индикатор перестаёт показывать live; при восстановлении SSE и история переподключаются.
9. Проверить доступ через SSH; запрос по внешнему адресу сервера не должен соединяться с HTTP.

Приостановка БД — только испытание на тестовом сервере: записи этого интервала будут потеряны.

## Измерение нагрузки

На целевом VPS сначала зафиксируйте модель CPU, ядро Linux, RAM, диск, фоновые приложения и их нагрузку. Выполните одинаковую нагрузку без наблюдателя, затем с GoInMetrics и одним зрителем, затем с несколькими зрителями. Длительность и профиль нагрузки должны совпадать. Отдельно измерьте влияние широких запросов истории.

```bash
./scripts/measure.sh 60 > measurements.txt
```

Скрипт выводит CPU/RAM/IO **обоих** контейнеров, состояние API и размер БД. Снимки `docker stats` не заменяют контрольное испытание до/после и не доказывают верхнюю границу ресурсов. Сохраните результаты через сутки работы: это проверяет срок хранения и реальный размер JSONB, который зависит от числа ресурсов. Текущая реализация не содержит вымышленных процентных гарантий минимальной нагрузки.

## Результаты реализации · 18 ноября 2026

Проверено в рабочем окружении Linux x86_64, ядро 6.17.0-35-generic, 12 логических CPU, около 7,1 GiB RAM:

- `go test -race ./...`, включая выделенную PostgreSQL: успешно; `go vet ./...`: успешно.
- `npm run typecheck` и `npm run generate`: успешно.
- `./start.sh`: оба контейнера healthy; случайный `.env` имеет права 0600. PostgreSQL `listen_addresses` пуст, приложение слушает loopback, UID 65532, корень read-only.
- Имя хоста, число CPU и файловые системы из контейнерного API сопоставлены с Linux-хостом; ошибок источников нет.
- Chrome: реальные метрики, изменение правила, навигация, выбор периода и пауза; 390 px без горизонтальной прокрутки; ошибок JavaScript нет. Финальная проверка также подтвердила скачивание CSV и отсутствие ложного сообщения об обрыве на паузе.
- Отказ тестовой PostgreSQL: health 503, живые снимки продолжаются, пять несохранённых измерений учтены; после возобновления запись восстановилась автоматически.
- Интеграционный тест проверил историю и события после повторного открытия БД; дополнительно основной контейнер приложения перезапущен с сохранением истории и правил.

В одном коротком наблюдении `docker stats` показал Go 7,5 MiB RAM / 0,08% CPU и PostgreSQL 20,4 MiB RAM / 0,19% CPU; локальный ответ snapshot занял около 0,55 ms, history — 4,7 ms. БД после нескольких минут работы занимала около 8 MiB. Это **единичный снимок на этой машине**, без контроля фона и сравнения до/после. Не является SLA, результатом испытания на малом VPS или суточного нагрузочного теста. Суточная стабильность, очистка под длительной нагрузкой и реальный эффект на наблюдаемое приложение требуют отдельного прогона на целевом сервере.
